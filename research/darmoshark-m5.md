## デバイス構成

| 部品 | VID:PID | 備考 |
| --- | --- | --- |
| 8K NRF Dongle | 1915:0725 | 「8K NRF Dongle」。設定エンドポイント iface 3 (usagePage 0xFF0A, usage 1) |
| 1K NRF Receiver | 1915:0723 | 電源ドライバー文書の対象機 |
| M5 マウス本体 | (1915:0716) | ドングルのハンドシェーク応答に現れる本体PID。有線時は 0x0737 と推定（公式productFirmwareテーブル: `M5 → 0x0737`） |

HIDレポートディスクリプタ (iface 3): 入出力とも**65バイト**（レポートID 0x00 + 64バイトデータ）。
Windows/hidapiでは読み取り時は先頭0x00が除去され64バイトが返る。

## トランスポート（これが最大の難所だった）

```
書き込み: [0x00][64バイトフレーム]  ← 65バイトで書くこと！
読み取り: 64バイトフレーム（hidapiが先頭のレポートIDバイトを除去）

フレーム: [0]=type [1]=index [2]=opcode [3]=sub [4..62]=payload [63]=チェックサム
チェックサム: 0xA1 - (バイト0..62の総和) & 0xFF  （フレーム全体の総計が0xA1になる）
type bit6 (0x40): 2.4GHzワークモード印。ドングル経由ではコマンドIDに焼き込む
  （ハンドシェーク初期コマンドのみ 0x00 で送る）
```

> **教訓**: 64バイトで書くと、hidapiがフレーム先頭バイト（type）をレポートIDと解釈し、
> データが1バイトずれたゴメージになる。ドングルは `1F 00 81 01`（後述のNACK）を
> 返し続ける。type=0（getVersion）だけはレポートID0として偶然有効で、チェックサムも
> 偶然合うため「一部だけ動く」という極めて分かりにくい症状になる。
> WebHIDは `sendReport(0, frame64)` で常に正しい形式で送るため、公式ドライバーは
> 問題なく動く。気づくきっかけは、公式ドライバーをローカルミラーで動かし、
> サーバーの404ログから「ブラウザーのハンドシェークは毎回届いている」ことを確認したこと。

## コマンド表（実機検証済み）

要求 `[type, 0, opcode, sub, payload…]`。応答は `(type & ~0x40, sub)` をエコー
（opcodeは一致しないのが正常）。**ドングルはマウスのスリープ中も全コマンドに応答する**
（設定ブロックはドングルが保持・リレーする）。

| コマンド | type | opcode | sub | 応答・備考 |
| --- | --- | --- | --- | --- |
| receiverState | 0x01 | 0x81 | 0x01 | f[4] bit3=リンク状態（1=結線）, f[5..6]=VID, f[7..8]=ドングルPID, f[9]=最大ポーリングコード, f[11..12]=マウスPID |
| battery (power) | 0x41 | 0x81 | 0x01 | f[5]=充電状態, f[6]=残量%, f[7]=プロファイル, f[8]=現在DPIステージ, f[9]=ポーリングコード, f[10]=最大コード, f[15..16]=現在DPI値(le16) |
| getBaseInfo | 0x44 | 0x81 | 0x01 | 設定ブロック全体（下記レイアウト） |
| getLight | 0x45 | 0x81 | 0x01 | f[5]=モード(0-6), f[7]=明るさ, f[9]=速度, f[11..13]=RGB×3ゾーン |
| getVersion | 0x40 | 0x81 | 0x00 | f[4..5]=マウスPID, f[9]=FWメジャー, f[8]=FWマイナー（高低ニブル分割: 0x15→"1.5"） |
| getBtn(i) | 0x43 | 0x82 | 0x03 | payload=[i]。f[5]=タイプ, f[7..]=キー割当（左f0/右f1/中f2/進f3/戻f4…） |
| setDpi | 0x44 | 0xB5 | 0x02 | payload = 設定ブロック [4..54]（下記） |
| setReportRate | 0x44 | 0x84 | 0x04 | payload=[コード 1-6 → 125/500/1000/2000/4000/8000Hz] |
| setExtConf | 0x44 | 0x84 | 0x0A | payload=[フラグ, LOD, アングル調整] |
| setBtnTime | 0x44 | 0x86 | 0x0E | payload=[スリープ秒 le16 ×2, デバウンスms] |
| setLight | 0x45 | 0x91 | 0x02 | payload=[01, モード, 07, 明るさ, 01, 速度, 01, R,G,B ×3ゾーン] |
| switchProfile | 0x42 | 0x82 | 0x01 | payload=[プロファイル番号] |
| saveData | 0x4A | 0x81 | 0x01 | フラッシュへ保存。**書き込みコマンドのたびに送る** |
| factoryReset | 0x49 | 0x81 | 0xFF | 約1.3秒待ってsaveData→再読み出し |
| （未実装） enterPair | 0x1D | 0x8B | — | ボンド照会 (sub 1, payload=PID) → f[5..9]=MAC。ペア送信は type 0 opcode 0x8B sub 5 |

**NACK**: type 0x1F（0x40付き要求には 0x5F）で `1F/5F 00 81 <エラーコード>` を返す。
実測: sub 0x05 = ワークモード不一致（0x40ビット無しでtype≠0を送った）、
sub 0x08 = 引数不正（setLightのモードに範囲外の値）。

## getBaseInfo 設定ブロックレイアウト（image[0..63]）

```
[4]    sysフラグ bit0=アングルスナップ bit1=センサー高性能 bit4=リップル制御
       bit5=モーションシンク bit6=eスポーツモード bit7=スクロール方向反転
[5]    ポーリングコード 1-6（読み出し値をそのまま書き戻す）
[6]    有効DPIステージマスク（1段=0b1, 2段=0b11 … 5段=0b11111）
[7]    現在のDPIステージ (0-4)
[8..27] DPI 5段階 × [xLo,xHi,yLo,yHi]（X/Y独立le16。実機は X=Y で運用）
[28..42] 5段階のステージカラーRGB（セットコマンドは未発見のため読み取り専用）
[43]   LOD (0=低0.7mm / 1=中1mm / 2=高2mm)
[44]   アングル調整（符号付き。0で未使用）
[50..53] スリープ秒 le16 ×2コピー
[54]   デバウンサ ms
```

## スリープ・応答特性

- マウス本体は無操作600秒（既定）でスリープする。
- **スリープ中もドングルは全読み書きコマンドに即座に応答する**（実機検証済み —
  スリープ中にsetLightを送り、LEDが変化することで適用も確認）。
- `01 00 8C 01` / `41 00 8E 01` はリンク状態・電源状態の非同期通知としても
  飛んでくる（公式ドライバーのhandleUpdateはこれをステータス更新に利用）。

## 解析の足跡（詰まったポイント）

1. **全コマンドが `1F 00 81 01` で拒否される** — 原因は上記の65バイト書き込み問題。
   3日分に相当する試行錯誤（0x40ビットの有無、スリープ状態、ワークモード理論など）
   はすべてこの1バイトに集約される。レポートディスクリプタ（65バイト長）を
   `dump-hid-caps.ps1` で確認していたのに、hidapiの書き込み前処理（先頭バイトの
   解釈）まで思い至らなかった。
2. **getVersionだけ動く** — レポートID0が偶然有効＋ずれたデータのチェックサムが
   偶然0xA1に合致（0x81+0x20）したため。偶然が迷路を深くした。
3. **公式ドライバーでの実証** — ローカルミラー+モックAPI（`vpId/420808485`=ドングル
   自身のIDが必要だった）で公式アプリを動かし、サーバー404ログから「ブラウザーの
   ハンドシェークは毎回成功している」ことを確認 → 差分は送出バイト数だけと特定。
4. **setLightの引数マップ** — 公式コードの呼び出し側で `{i: lightMode, l: brightness,
   s: speed}` であることを確認（frame上では [5]=モード [7]=明るさ [9]=速度と
   読み取りと同位置）。誤って i=0x40 をモードに送ると sub 0x08 のNACK。

## 対応機能（devices/darmoshark-m5.json）

プロファイル切替（5枠）／DPI 5段階（X=Y、50〜26000）／ポーリング 125〜8000Hz／
LOD 3段階／アングルスナップ／センサー高性能／リップル制御／モーションシンク／
eスポーツモード／スクロール方向反転／スリープ 60〜3600秒／デバウンサ 0〜32ms／
ライト7モード+カラー+明るさ+速度／工場リセット。バッテリーは常時ポーリングで表示。

未対応: ステージカラーの変更（セットコマンド未発見）、ボタン割当・マクロ
（getBtnで読めることは確認済み、コマンド形式は公式バンドル参照で追加可能）、
有線接続（0x0737、ワークモード0x00で送る必要がある）。
